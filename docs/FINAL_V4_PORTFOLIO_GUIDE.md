# TREND RADAR 2.0 — PORTFOLIO GUIDE

작성일 2026-11-05 · PHASE 9. 포트폴리오에 옮겨 쓸 때 **측정하지 않은 성과(사용자 수, 만족도, 제작 시간 단축률 등)는 쓰지 않는다.** 이 문서에도 그런 수치는 없다.

## 1. PROJECT OVERVIEW
TREND RADAR는 한국 2030의 온라인 문화에서 **지금 무엇이 일어나고 있는지** 실제 데이터로 발견하고, 왜 주목받는지 근거와 함께 해석한 뒤, 그 해석을 카드뉴스·숏폼 콘텐츠와 편집 가능한 Figma 디자인까지 이어 주는 문화 인텔리전스 웹 서비스다. 다음 자료를 근거 원장으로 묶고, AI는 원장에 있는 근거 ID로만 주장을 인용한다.
- NAVER 검색 관심도
- Instagram 해시태그 게시물
- YouTube 공개 영상
- 웹 출처

관찰 사실, 출처 기반 해석, AI 가설을 화면에서 구분해 보여 준다.

## 2. PROBLEM DEFINITION
- 트렌드 도구는 대개 "검색량이 올랐다"에서 멈춘다. 기획자가 실제로 필요한 것은 **어떤 행동이 관찰되는지, 왜 지금인지, 무엇을 만들 수 있는지**다.
- 생성형 AI에 트렌드 콘텐츠를 맡기면 다음 두 가지가 생기기 쉽다.
  - 키워드의 역사·입문 소개 같은 **일반적인 글**이 나온다.
  - 근거 없는 사실이나 유행 주장을 **지어낸다**.
- 분석 결과를 실제 디자인 작업(Figma)으로 옮기는 과정이 수작업이다.

## 3. DESIGN OBJECTIVE
1. **근거가 보이는 해석:** 모든 주장에 출처 상태(관찰 / 출처 보도 / AI 가설)를 붙인다. 근거 없는 주장은 낮춘다.
2. **현상 중심의 콘텐츠:** 키워드 설명이 아니라 관찰된 구체적 장면·행동으로 콘텐츠를 만든다.
3. **편집 가능한 결과물:** 텍스트·이미지가 분리된 Figma 레이어, 사용자의 템플릿 사용.
4. **비용·데이터 안전:** 유료 API는 사용자가 누를 때만 호출한다. 결과를 캐시·저장하고, 사용자 데이터를 격리한다.

## 4. USER FLOW
- **단일 트렌드:** Discover(키워드) → (세부 현상 선택) → WHY → Content Studio → Figma
- **결합(선택 경로):** WHY 분석한 트렌드 2개 → DNA 분해 → Collision / Creative Collision(SAFE·BOLD·WILD) → (Trend Lab 검토) → Content Studio → Figma
- **연결 탐색:** Trend Web / Culture Map에서 두 신호의 관계 확인 → Creative Collision 또는 Studio
- **이어 하기:** Workspace(브라우저 + Supabase 계정)에서 저장한 분석·프로젝트를 다시 연다.

## 5. KEY FEATURES (5개)
1. **LIVE WHY 분석:** 검색 추이·Instagram·YouTube·웹 출처로 근거 원장을 만들고, OpenAI가 원장 ID로만 원인 가설을 제시한다.
2. **세부 현상 발견(WHAT'S HAPPENING NOW?) · Trend Web:** 키워드 안에서 최근 관찰된 구체적 현상과 연결 신호를 찾는다.
3. **Creative Collision:** 두 트렌드의 DNA·근거를 바탕으로 SAFE·BOLD·WILD 아이디어를 만든다. 실제 연결과 창작 가설을 구분한다.
4. **Content Studio(Editorial Engine):** 방향 5개 제안 → 사용자 선택 → 스토리보드 → 카드뉴스·숏폼. 생성 후 결과를 필수 규칙으로 검사하고, 편집 리뷰가 고쳐 쓴다. 슬라이드별 AI 이미지도 만든다.
5. **Figma 연동:** 플러그인이 AUTO DESIGN 또는 사용자의 MY TEMPLATES에 콘텐츠를 넣는다. 원본 템플릿은 보호하고, 미리보기를 렌더링·동기화한다.

## 6. AI & DATA ARCHITECTURE
| 구성 | 역할 | 비고 |
|---|---|---|
| NAVER DataLab | 지정 키워드의 상대 관심도 | 새 키워드 목록은 주지 않음(문서에 명시) |
| Instagram Graph API | 해시태그 게시물 표본·이미지 | 승인 범위 안에서만. 새 해시태그 조회는 사용자 행동으로만 |
| YouTube Data API | 공개 영상 신호 | 조회수를 원인으로 단정하지 않음 |
| OpenAI(Responses API, web_search) | 해석·현상 발견·방향 제안·제작·편집 리뷰·이미지 | 구조화 출력(JSON Schema) + 서버 검증(Zod) |
| 근거 원장 | 모든 근거에 ID를 붙인다 | 원장에 없는 ID 제거, 근거 없는 주장은 `Insufficient Evidence` |
| 규칙 검사(editorial-quality) | 필수 9개를 검사한다(사실, 주제, 언어, 근거 ID, 중복, 허위 경험, 근거 없는 유행, 게시 문구의 자료 한계, 출처 서술) | AI 점수와 분리 |
| 비용 보호(ai-guard) | 동일 입력 캐시, 동시 요청 병합, 분당·일일 상한 | 서버 메모리 기준 |
| Supabase | 로그인, RLS 사용자별 저장, 비공개 이미지 버킷, 플러그인 토큰(해시) | 관리자 키는 서버에만 |
| Figma 플러그인 | 작업(JSON)을 받아 편집 가능한 프레임으로 그림, 템플릿 동기화 | 네트워크는 Supabase만 허용 |
| 스택 | Next.js 16 · React 19 · TypeScript · Zod · Playwright | 테스트 960개(49개 파일, 브라우저 2종) |

## 7. UX DESIGN DECISIONS
- **데이터 상태를 늘 표시:** LIVE / SAVED / DEMO / AI 가설 배지. 데모를 실제처럼 보이지 않게 사선 줄무늬로 표시한다.
- **유료 호출은 버튼 하나에 하나:** 버튼에 "새 API 호출", 이미지 생성 확인 창을 둔다. 저장 결과는 무료로 다시 연다.
- **조용히 바꾸지 않기:** 요청한 Collision·트렌드·프로젝트를 못 찾으면 다른 것으로 대체하지 않는다. 무엇이 없는지와 고칠 방법을 보여 준다.
- **목적에서 시작:** 온보딩에서 찾기 / 아이디어 / 제작 중 목적을 고른다. 진행 막대는 기본 경로와 선택 단계를 구분한다(V4).
- **근거가 부족할 때 고를 수 있게:** 지어내지 않고 대안 A~E를 제시한다(V4).
- **게시용과 제작자용 분리:** 검증 메모·자료 한계는 EDITOR NOTES에만 둔다.
- **디자인 시스템:** Y2K Pixel Desktop(창·타이틀바·스티커 그림자)을 화면 전체에서 일관되게 쓴다.

## 8. ITERATION PROCESS (실제 기록)
| 회차 | 발견 | 원인 | 수정 | 재검증 |
|---|---|---|---|---|
| Editorial V2→V3 | 카드뉴스가 "입문은 응원가부터" 같은 일반 가이드가 됨 | 방향 제안의 기본값이 키워드 역사·입문 | 방향마다 초점·대표 장면, 역사·입문 방향 검사 | 실측 9회 호출: 역사·입문 방향 0개 |
| V3 실측 | 치이카와 결과에 "현재 자료에는…" 문구 | 근거 없는 방향 + 약한 지시 | 필수 검사·지시 추가, V4에서 사전 대안 안내 | **재생성 미실행** |
| MY TEMPLATES | Figma에서 이미지가 회색에 가려짐 | 템플릿의 불투명 단색 채우기가 이미지 위에 있음 | 단색 기본 채우기를 이미지로 교체 | 실제 Figma 검증 파일에서 확인 |
| Collision → Lab | 다른 Collision이 열림 | URL ID를 못 찾으면 첫 항목으로 대체 | 직접 조회, 누락 안내, 계정 복원 | 회귀 테스트 18개 |
| V4 P0 | 저장 공간이 차면 작업이 사라짐 | 저장 실패를 화면이 모름 | 공통 경고 막대 | 저장 공간 가득 참 재현 테스트 |
| V4 3차 | Creative Collision이 요청과 다른 트렌드를 선택 | 저장 분석을 읽기 전에 선택값을 정함 | 읽은 뒤 선택, 누락 안내 | 흐름 테스트 |

## 9. FINAL OUTPUT
- 실측 카드뉴스 원고(저장 기록): Roblox × Makeup "게임 속 눈매를 현실 얼굴로 옮기면"(필수 검사 전부 통과, 6장 모두 다른 이미지 장면), KIA "응원 동작이 영상 속 춤으로 옮겨갈 때".
- Figma: AUTO DESIGN 프레임과 MY TEMPLATES 렌더링. **포트폴리오용 캡처는 사용자 Figma 파일에서 직접 만들어야 한다.** 이 문서 작성 시점에 실제 사용자 파일의 최종 결과는 확인하지 않았다([QA 보고서](FINAL_V4_QA_REPORT.md) 미확인 목록).
- 넣으면 좋은 자료(사용자가 준비): 화면 캡처(온보딩, WHY, Studio, Figma 결과), 실제 생성 카드뉴스 전후 비교 한 쌍.

## 프로젝트 기여도 작성 가이드

포트폴리오에서는 **본인이 한 일**과 **AI 도구(Claude Code 등)가 한 일**을 나눠 적는다. 아래는 이 저장소와 작업 기록에서 확인되는 것을 바탕으로 한 틀이다. 본인 기억과 다르면 고쳐서 쓴다.

| 영역 | 본인(기획자·디자이너) | AI 코딩 도구 |
|---|---|---|
| 문제 정의·목표 | 서비스 방향, 단계별 요구사항(T0~T8, Editorial V3, FINAL POLISH V4 등) 작성 | 요구사항에 따른 진단 문서 작성 |
| 품질 기준 | "역사·입문 강요 금지", "자료 부족을 게시 문구에 쓰지 않기" 같은 편집 원칙 결정 | 원칙을 규칙 검사·프롬프트로 구현 |
| 디자인 | Y2K Pixel Desktop 방향, Figma 템플릿(TEMPLATE_COVER/BODY/CTA) 제작 | 화면 코드 구현, 플러그인의 템플릿 적용 로직 |
| 검증 | 실사용 중 버그 발견(Collision 오선택, 저장 실패, IMAGE_1 미인식 등), 외부 검수(GPT 리뷰용 패키지), 유료 실행 승인 | 자동 테스트 작성·실행, 원인 분석·수정 |
| 인프라 | Supabase 프로젝트·마이그레이션 실행, API 키 발급·관리 | 마이그레이션 SQL·보안 규칙 작성 |
| 의사결정 | 기능 범위, 커밋·배포 시점, 비용 승인 | 선택지와 권장안 제시 |

**쓰는 요령**
- "AI 플랫폼을 만들었다"보다 **무엇을 판단했고 무엇을 검증했는지** 적는다. 예: 문제를 발견하고, 원칙을 정하고, 결과를 비교해 다음 지시를 냈다.
- 코드 작성에 AI 도구를 썼다면 그대로 밝힌다. 커밋에는 `Co-Authored-By: Claude` 표기가 있다.
- 수치는 측정한 것만 쓴다.
  - 쓸 수 있는 수치: 테스트 수, 실측 호출 수, 규칙 검사 결과
  - 쓰면 안 되는 수치: 사용자 수, 만족도, 시간 단축률 같은 추정치
