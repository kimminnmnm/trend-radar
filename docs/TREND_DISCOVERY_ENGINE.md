## T1. 세부 현상 발견 — `POST /api/discover/phenomena`

입력: 키워드, 관측 기간(7/30/90일 또는 3~180일). 수집: YouTube(기간 안, 관련도순) · OpenAI 웹 검색(기간 안의 하위 스타일·챌린지·포맷·협업·행동, 정의·역사 페이지 제외, 실제 조회 URL만) · NAVER(후보 검색어 최대 5개, 모멘텀용). Instagram은 해시태그 주간 할당량 보호로 새로 검색하지 않는다.

후보 필드: signalId · parentKeyword · title · phenomenon · audienceBehavior · relatedEntities · relatedKeywords · contentExamples · observedPlatforms · evidenceIds · observedDateRange · evidenceStrength · momentumIndicator · verificationStatus.

서버 판정(`lib/discovery.ts`): 원장에 없는 ID 제거 → 키워드 일반 설명·역사는 제외 → **관측 기간 안 근거의 독립 출처 수**로 Observed(2+) / Emerging Signal(1) / 제외(0). 강도: strong(3+ & 플랫폼 2+) / moderate(2+) / weak. 모멘텀은 NAVER 상대 지수(최근 4주 ÷ 이전)로만, 없으면 null. "급상승·바이럴·1위"는 근거가 말할 때만.

## T2·T3. 관계 구조와 실제 연결 — `POST /api/discover/connections`

1. 검색어 확장(OpenAI): 두 대상의 별칭·관련 범주어와 **방향이 다른 3~5개 가설**별로 행동이 들어간 검색어(한·영).
2. YouTube 2회(한국어 1 · 영어 1, 기간 안) + OpenAI 웹 검색 1회(두 개념이 같은 콘텐츠에 함께 나오는 출처만).
3. 추출: 현상마다 Subject · Action · Object · Direction · Platform · Context · Evidence. 방향이 다르면 합치지 않고, 브랜드 체험과 사용자 창작은 분리.
4. 서버 판정: 두 개념이 함께 나오는 근거의 독립 출처 2+ → **OBSERVED CONNECTION**, 1 → **EMERGING SIGNAL**, 0 → **CREATIVE HYPOTHESIS**. 최신성(기간 안 / 날짜 미상 / 기간 밖)은 따로. 검색 계획의 방향 중 근거를 못 찾은 것은 "근거 미발견 가설"로 남긴다.

## 남은 문제 (T4로 가기 전)
- 표본이 작다(YouTube 검색 1~2회·웹 검색 1회). 대부분 후보가 독립 출처 1개라 Emerging Signal이다. 표본을 늘리면 비용이 는다.
- 2차 실행에서도 브랜드 체험이 사용자 창작과 한 현상에 섞인 항목이 있었다 → 추출 지시를 보강했지만 재실행으로 확인하지 않았다.
- 계획 방향과 결과의 중복 판정은 이름·글자 유사도 기준이라 완벽하지 않다.
- 웹 출처 요약은 AI 요약이며 원문 확인이 필요하다.
- WHY 재정의, Studio 맥락 고정, 이미지 의미 정렬(T5~T7)은 아직 구현하지 않았다.

## T4. Overview "WHAT'S HAPPENING NOW?" — `components/happening-now.tsx`

새 엔진 없이 기존 `/api/discover/phenomena`(서버 12시간 캐시)를 Overview에 연결했다.

**T4.1 카드** — 현상 이름 · 핵심 행동 · 현상 설명 · 관련 키워드 · 관측 플랫폼 · 관측 기간(근거 날짜 범위) · 출처 수(독립 출처, 1곳이면 "단일 출처") · 근거 건수 · VIEW EVIDENCE로 원장 근거(제목·출처·날짜·발췌·원문 링크) · 관련 이미지(근거 YouTube 영상의 공식 썸네일, 없으면 그리지 않음).

**T4.2 상태** — OBSERVED(독립 출처 2곳+) / EMERGING(1곳) / INSUFFICIENT EVIDENCE(후보였지만 관측 기간 안 근거가 없거나 확인 불가. 배경·역사 설명과 중복은 여기 넣지 않음). 화면에 "상태는 인기도나 검색량 증가를 뜻하지 않습니다"를 고정 표시. 상승률은 NAVER DataLab 데이터가 있는 현상에만 "상대 지수 · 절대 검색량·순위 아님"으로 표시, 인기 순위는 표시하지 않는다.

**T4.3 선택** — EXPLORE WHY · VIEW EVIDENCE · CREATE CONTENT · SAVE TO WORKSPACE. WHY·Studio 주소에 `phenomenon`(현상 ID) · `kw` · `title` · `behavior`(핵심 행동) · `from`/`to`/`days`(관측 기간) · `ev`(근거 ID) · `status` · `src`를 싣는다(`phenomenonQuery` / `phenomenonFromQuery`, 형식이 틀린 값은 버림). Studio는 브라우저에 발견 결과가 없어도 주소만으로 맥락을 복원하고, 프로젝트에 `phenomenon` 맥락을 저장해 상단에 표시한다. Workspace 저장은 기존 saved_items(insight 유형, payload `kind: "phenomenon"`)를 써서 클라우드 동기화도 그대로 된다.

**T4.4 데이터** — 버튼을 눌러야만 호출, 결과는 브라우저(`trend-radar-discoveries`, 최근 20개, 계정 격리)에 저장해 다시 열 때 호출하지 않음. 7일이 지난 저장 결과는 "N일 전에 수집" 경고. 오류(401·500·형식 오류)여도 이전 결과와 Overview의 다른 섹션은 그대로.

## T5. Context-Aware WHY — 선택한 현상 자체를 분석

**T5.1 전달** — `PhenomenonContext`(`lib/schemas.ts`의 Zod 스키마 하나로 API 입력·리포트 저장·주소 복원에 공용): Parent Keyword(`keyword`) · 현상 ID · 이름 · Subject · Action · Object · Direction · Cultural Context · 관측 기간 · 근거 ID · 근거 상태 · 출처 수 · 검색어. 발견(T1) 후보는 주체·대상을 따로 뽑지 않으므로 빈 값으로 두고(지어내지 않음), 연결(T3)에서 고른 현상은 주체·행동·대상·방향을 그대로 쓴다(`phenomenonContextOfConnection`). `/api/analyze`에 `phenomenon`이 없으면 기존 키워드 분석 그대로.

**T5.2 검색** — 현상 모드(`analyzePhenomenon` in `app/api/analyze/route.ts`):
- 발견 단계 근거를 재사용(현상 근거 ID에 있는 것만, `D-xx`로 다시 번호).
- 재사용 근거가 3건 미만일 때만 기본으로 추가 검색: YouTube(현상 검색어, 관측 기간, 관련도순) · 웹(현상 행동을 한·영으로 검색, 상위 키워드 단독·역사·정의·다른 방향 자료 제외 — `collectWebEvidence(..., phenomenon)`). 사용자가 켜고 끌 수 있다.
- NAVER는 현상 검색어(20자 이하)로, 실패해도 분석은 계속. Instagram 해시태그 검색은 쓰지 않음(현상 이름은 해시태그가 아님, 할당량 보호).

**T5.3 분석** — 프롬프트 `why-phenomenon-v1`: WHAT · WHO · HOW · CULTURAL CONTEXT · WHY NOW · EVIDENCE. 기원은 선택 사항(모르면 "확인하지 않음"). 상위 키워드 일반·다른 방향 근거로 현상을 뒷받침하지 않음. EMERGING이면 유행·인기 표현 금지. 서버 결정적 검사 `checkPhenomenonFocus`: WHAT·대표 요약에 현상 핵심어가 있는지, 역사·기원 설명으로 이탈했는지, 제한적 신호를 유행으로 표현했는지 → 경고로 표시(자동 재생성 없음).

**T5.4 화면** — WHY 상단 "ANALYZING PHENOMENON" 배너(이름 · Parent Keyword · Evidence Status · 관측 기간 · 근거 ID · 주체·행동·대상·방향·문화 맥락 · 재사용 근거 수 · 검사 경고) + "원래 키워드 전체 분석으로 전환". 리포트에 WHO·HOW 카드 추가.

## T6. Editorial Context Lock — `lib/editorial-lock.ts`

**필드(프로젝트 `contextLock`)** — selectedPhenomenonId · selectedPhenomenon · coreBehavior · culturalContext · editorialFocus · observedEvidenceIds · creativeHypothesis · prohibitedTopicDrift (+ parentKeyword · subject · object · direction · evidenceStatus · userMaterials · enabled).
